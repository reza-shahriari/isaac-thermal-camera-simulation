Research findings by topic#

GPU / texture-space temperature fields and per-pixel attribute transport#

24 findings.

  • Warp 1.16.0 — the version bundled in this Isaac Sim build — provides wp.mesh_query_point_no_sign(mesh, point, max_dist) and wp.mesh_query_point_sign_normal(...) returning a MeshQueryPoint with fields result, sign, face (int32 triangle index), u, v (barycentric), plus wp.mesh_eval_position(mesh, face, u, v) to reconstruct the surface point. mesh_query_ray returns the same plus t and normal. source: Installed source, primary: /home/hunter/IsaacSim/.pixi/envs/runtime/lib/python3.12/site-packages/warp/_src/types.py lines 7579-7640 (MeshQueryPoint / MeshQueryRay) and _src/builtins.py lines 8398-8470; warp/config.py reports version 1.16.0 for irsim: This is the missing piece ADR 0087 assumed did not exist. A pixel's float32 world position (Camera3dPositionSD) plus the prim's mesh gives (face, u, v) — an exact surface parameterisation of arbitrary curved geometry — with no renderer capability, no UV AOV, no per-triangle AOV, and no asset authoring. PlanarPatch's plane projection becomes the degenerate case of this query.
  • Measured on this machine: 327,680 closest-point queries (640x512 pixels) against a 516,960-triangle mesh take 0.63 ms on an RTX 5090; against 128,880 triangles, 0.51 ms. 327,680 mesh_query_ray calls take 0.51 ms. LBVH build for the 517k-triangle mesh: 0.9 ms (the 40 ms figure on the first mesh includes one-time warm-up). source: Local benchmark I wrote and ran: /tmp/claude-1000/-home-hunter-irsim-scaffold/694d9084-3af5-4c5a-aaad-2d2f8abcf990/scratchpad/warp_bench.py (Warp 1.16.0, CUDA 12.9, RTX 5090) for irsim: Cost is not an argument against the mesh route. Sub-millisecond per frame at sensor resolution is three orders of magnitude under the radiance kernels, and the BVH can be rebuilt every frame for moving geometry. It also prices ray-traced per-cell sky-view/shadowing and form factors (ADR 0088's 'revisit when') at about 0.5 ms per 327k rays.
  • wp.Mesh accepts velocities, groups (per-triangle group ids) and bvh_constructor ('sah'|'median'|'lbvh'|'cubql'), and exposes refit() for deforming geometry. Grouped meshes offer mesh_get_group_root, but only the ray query builtins take a root argument in 1.16 — mesh_query_point_no_sign has no root parameter. source: Installed source, primary: warp/_src/types.py Mesh.__init__ (line ~5874) and refit() (line ~6029); warp/_src/builtins.py mesh_get_group_root (line 8123), ray-query root docs at lines 8826/8865/8930/8988 for irsim: Closest-point queries cannot be restricted to one prim's triangles inside a shared BVH, so build one wp.Mesh per bound prim. That is the right design anyway: the per-pixel instance id selects the mesh, which exactly removes the closest-point ambiguity on thin two-sided panels and on a car sitting on a road — the same failure ADR 0087's thickness_m slab exists to prevent, solved structurally instead of by a tuned half-width.
  • USD carries texture coordinates as the primvars:st primvar, typically with faceVarying interpolation and indexing (one value per face-vertex, indices used to express seams). UsdGeomPrimvar exposes ComputeFlattened() and the index array. source: https://openusd.org/release/user_guides/primvars.html and https://openusd.org/docs/api/class_usd_geom_primvar.html for irsim: Given (face, u, v) from the Warp query, irsim can interpolate the asset's own UVs itself and obtain a per-pixel UV — no UV AOV needed. This unblocks ADR 0087's rejected option 1 (temperature as a texture) without waiting on any renderer feature. Note the known OpenUSD gotcha that ComputeFlattened() returns raw samples for time-sampled faceVarying primvars (issue #238).
  • The Omniverse RTX renderer's debug/'View' list contains PT AOV World Position, World Normal, View Normal, Z-Depth, motion vectors and lighting decompositions — and no texture-coordinate/UV view, no primitive or triangle id view, no object-space position view, and no barycentric view. (medium confidence) source: https://docs.omniverse.nvidia.com/materials-and-rendering/latest/rtx-renderer_common.html for irsim: Independent corroboration of ADR 0014's measurement from the vendor docs rather than only from the probe. Confidence is medium because the Views UI list is not necessarily the full RenderVar registry, but it is consistent with what the probe found. Do not spend a step trying to find a UV AOV; spend it on the closest-point bridge, which needs none.
  • Isaac Sim 6.0's RTX sensor objId is a 128-bit stable id built by combining 'a per-instance base stable ID with an upper index placed in the high 32 bits — the submesh index for mesh geometry, and the per-triangle primitive index for procedural geometry'. The StableIdMap AOV registers per-instance entries plus per-GeomSubset entries when an instance has more than one subset, but 'does not register per-primitive entries'. Requires --/rtx-transient/stableIds/enabled=true. (medium confidence) source: https://docs.isaacsim.omniverse.nvidia.com/6.0.0/sensors/isaacsim_sensors_rtx_annotators.html for irsim: Two things. (a) A per-triangle primitive index does exist inside the renderer's id scheme — for procedural geometry — so ADR 0087's option 2 is closer than 'nobody has found an integer AOV'; it is worth a short probe on the RTX-sensor path. (b) More usefully today: splitting a mesh into GeomSubsets gives distinct ids below prim granularity, which is a zero-new-machinery way to give one object several thermal zones (wheel vs arch vs tyre) even before the mesh field lands.
  • DIRSIG (RIT, publicly documented) solves temperature per facet with THERM, which 'calculates temperatures separately for each object facet' and assumes 'each exhibits isothermal behavior over its entire surface'. Spatial variation within a surface is supplied by a separate Map Temperature Solver that 'uses raster image maps with UV projection to apply spatially-varying temperatures across surfaces', alongside per-facet temperatures imported from MuSES via TDF files. source: https://dirsig.cis.rit.edu/docs/new/temp_solvers.html and https://dirsig.cis.rit.edu/docs/new/thermal.html for irsim: The mature, publicly documented IR simulator has exactly irsim's defect (isothermal facets) and exactly the fix under consideration (a UV-projected temperature map). This is strong external validation of the direction and a concrete format model to copy: a float32 raster sampled through the asset's UVs, plus a per-facet path for imported solver output. It also means a Tier-4 comparison against DIRSIG-style published imagery is arguing on equal terms.
  • MuSES (ThermoAnalytics) predicts temperatures on a meshed CAD geometry — '3D surface/volume mesh with appropriate thermal material properties' — and 'generates radiance maps from predicted 3D temperature distributions' with BRDF-based ray tracing. (medium confidence) source: https://www.thermoanalytics.com/product/muses/ and https://blog.thermoanalytics.com/blog/muses-features-capabilities for irsim: Sets the industry bar: per-element temperature on the actual mesh, not per-object and not per-plane. Confidence is medium because these are product pages, not papers. Useful as the argument for why per-face/per-vertex storage (not a projected plane) is the end state.
  • Texture-space diffusion (the canonical games technique) renders the mesh into UV space by using texture coordinates as render coordinates, then blurs in 2D. It needs a stretch-correction texture built from screen-space derivatives of world position because 'distances between locations in the texture do not correspond directly to distances on the mesh due to UV distortion', and it needs explicit seam handling (duplicate edge polygons, alpha blend near seams, or a partition of unity) because seams sever the diffusion domain. Cost in the reference implementation: six irradiance textures, 6x2x7 = 84 texture accesses per output texel, consuming 'most of the resources of an entire GeForce 8800 Ultra'. source: GPU Gems 3, ch. 14, d'Eon & Luebke — https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-14-advanced-techniques-realistic-real-time-skin for irsim: If irsim ever solves lateral conduction in UV space, the metric correction and seam handling are mandatory and are the two things that quietly make the answer wrong while the image looks fine — precisely the class of error CLAUDE.md is written against. This is the strongest argument for keeping the solver on the mesh (per-face/per-vertex, exact adjacency) and using UV only as an authoring/lookup channel.
  • Stam's 'Flows on Surfaces of Arbitrary Topology' (SIGGRAPH 2003) solves PDEs in the parameter space of surface patches and 'uses the local metric (g_ij) computed directly from the parametrizations to counter distortions caused by parametrization', with an explicit treatment of cross-patch boundary conditions; the paper states the technique generalises to reaction-diffusion and other surface PDEs. source: Jos Stam, ACM TOG 22(3), 2003 — https://www.dgp.toronto.edu/public_user/stam/reality/Research/pdf/surfflow.pdf for irsim: The primary source for 'parameter-space simulation is only correct with the metric tensor'. If a UV-space heat solve is ever proposed in this repo, this is the citation that says a plain 2D Laplacian on the atlas is wrong, and by how much (the anisotropy of the chart's Jacobian).
  • Parameterisation-free per-surface storage is a solved, production-proven problem: Ptex stores a separate texture per face plus a per-face adjacency map in one file, requiring no UV assignment, and uses the adjacency for seamless filtering; Htex stores a square texture per halfedge and filters seamlessly with three texture fetches, natively supporting arbitrary polygons; Mesh Colors stores values at vertices, edges and face interiors with a per-face resolution R, allows local resolution change with no global effects, and in one reported example matched a 2D texture's quality with 20% less memory. source: Burley & Lacewell, Ptex, EGSR 2008 — https://media.disneyanimation.com/technology/opensource/ptex/ptex.pdf ; Baert et al., Htex, HPG 2022 — https://arxiv.org/abs/2207.05618 ; Yuksel et al., Mesh Colors (TOG 2010) / Mesh Color Textures (HPG 2017) — https://www.cemyuksel.com/research/meshcolors/ for irsim: These give exact, topology-aware neighbour lookup, which is what a conduction stencil needs and what a UV atlas destroys at seams. A Ptex-style 'per-face grid of cells plus adjacency' is the natural container for irsim's cells once they leave the plane, and the per-face resolution R maps directly onto ADR 0087's 'cell count is set by the thermal gradient, not the pixel count'.
  • Texel/texture-space shading is an established real-time decoupling pattern: texel shading records texel accesses as shading work on 8x8 tiles, uses a 'triangle index texture' mapping texels to their source triangles for attribute interpolation in compute, and caches/ages tiles for reuse across frames; reported up to 4.1x speedup but up to 64x cost blow-up if resolution selection mismatches the mip level. FastAtlas (CGF 2025) builds per-frame GPU atlases that pack only visible content at a constant texel-to-pixel ratio. source: Hillesland & Yang, Texel Shading (EG 2016) — https://gpuopen.com/learn/texel-shading/ ; Vining et al., FastAtlas, Computer Graphics Forum 2025 — https://arxiv.org/abs/2502.17712 for irsim: Two transferable lessons. (1) The 'triangle index texture' is the rasteriser's version of what the Warp closest-point query gives irsim for free. (2) The resolution-mismatch trap is the same one irsim faces: choose thermal cell size by the gradient (as ADR 0087 already argues) and decouple it from pixel size, but assert the relationship, because a cell much smaller than a pixel wastes solver time and a cell much larger than a pixel puts a visible staircase in the frame.
  • Unreal's Lumen approximates arbitrary meshes for its Surface Cache with a small set of flat 'Cards' — 12 by default per mesh, typically six to eight orientations — captured at low resolution into an atlas and relit each frame; its documented failure mode is the 'Lumen Surface Cache Gap' where geometry no card covers goes unlit. source: https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-technical-details-in-unreal-engine and https://unrealdirective.com/resources/unreal-decoder/artifacts/lumen-surface-cache-gap/ for irsim: This is the cheapest incremental step and it validates ADR 0087's choice rather than overturning it: production engines really do cover curved geometry with ~6-12 projected planar patches. irsim could get most of the way to a wheel or a fuselage by allowing N patches per prim with automatic orientation selection. But adopt Lumen's known artefact as a test: any bound prim must have every pixel claimed by some patch, which is exactly the condition point_bridge already raises on.
  • EA SEED's Global Illumination Based on Surfels (GIBS, SIGGRAPH 2021) discretises scene surfaces on the fly into disk-shaped surfels spawned in screen space and scaled to camera coverage, caches lighting in them and amortises it over time, 'requires no pre-computation, no special meshes, and no special UV sets'; it now ships in EA SPORTS College Football 25. source: https://www.ea.com/seed/news/siggraph21-global-illumination-surfels and https://www.ea.com/technology/news/gibs-lighting-ea-sports-college-football-25 for irsim: The most asset-agnostic option, and attractive because irsim will import assets with no UVs. But surfels are spawned by camera coverage and are transient, whereas a surface temperature is a memory built over a 48 h spin-up (facets.py). Surfels would have to be persistent and camera-independent, at which point they are just an unstructured per-face field with worse adjacency. Recommend against as the primary representation; note it as the fallback for unauthored background geometry.
  • Unreal's Runtime Virtual Texture renders texel data on demand at runtime into a UV-space target and reads it back in materials; the same 'render into unique UVs and keep the result' pattern is the standard game technique for persistent per-surface state (e.g. splatting wounds into a per-character render target), which requires a mesh with unique UVs and incurs spiky per-event GPU cost. (medium confidence) source: https://dev.epicgames.com/documentation/en-us/unreal-engine/runtime-virtual-texturing-in-unreal-engine and https://tomlooman.com/unreal-engine-render-character-wounds/ for irsim: Confirms that 'persistent state stored in UV space' is a mainstream, shipped pattern, and that its hard prerequisite is unique (non-overlapping, non-mirrored) UVs per object — which most imported USD assets do not have, since art UVs are routinely overlapped and mirrored to save texture space. Any UV-atlas route needs a validity check on the asset, not an assumption.
  • xatlas (MIT) generates unique UVs from raw triangle geometry in three stages — chart segmentation, LSCM parameterisation, atlas packing — with controls for padding, target resolution and texel density, and tolerates degenerate input. source: https://github.com/jpcy/xatlas for irsim: If irsim needs an atlas for assets that lack usable UVs, this is an offline, engine-free, pure-geometry step that fits under scripts/ and does not touch src/irsim. It is a build-time asset dependency, not a runtime one — but it is still a dependency and an asset-pipeline step, which is the cost the closest-point route avoids entirely.
  • Baking values into a UV atlas by rasterisation systematically misses texels whose centre is not covered by any triangle ('if a triangle does not overlap the texel center, it will be empty'); the remedies are conservative rasterisation (cover any partially overlapped texel) and gutter dilation, and post-hoc dilation over thin triangles itself produces artefacts. source: https://projects.blender.org/blender/blender/pulls/161752 (Blender conservative rasterization for texture bake) and https://ndotl.wordpress.com/2018/08/29/baking-artifact-free-lightmaps/ for irsim: A third correctness tax on the UV-atlas route, on top of metric distortion and seams. In a thermal image an empty texel is not a subtle artefact — it is a cold pixel on a hot panel. Per-face storage (Ptex/Mesh Colors) or the closest-point query has no such failure because every surface point maps to a cell by construction.
  • The cotangent Laplacian — the standard operator for diffusion on a triangle mesh — produces negative edge weights whenever the two opposite angles sum to more than pi (obtuse, non-Delaunay triangles), which breaks the discrete maximum principle that prevents interpolated values from leaving their bounds. Wardetzky et al.'s 'no free lunch' theorem shows no discretisation has all desirable properties at once; Sharp & Crane's 'tufted cover' + intrinsic Delaunay flips give a drop-in Laplacian 'guaranteed to have nonnegative edge weights ... even for extremely poor-quality meshes', with open-source code and Python bindings. source: Wardetzky, Mathur, Kälberer & Grinspun, SGP 2007 — https://www.cs.columbia.edu/cg/pdfs/1180993110-laplacian.pdf ; Sharp & Crane, SGP 2020 — https://www.cs.cmu.edu/~kmcrane/Projects/NonmanifoldLaplace/NonmanifoldLaplace.pdf ; https://github.com/nmwsharp/nonmanifold-laplacian for irsim: If irsim adds lateral conduction on the mesh (and the diffusion-length finding below says it should for metal), the operator choice is load-bearing: a plain cotan Laplacian on an imported, non-Delaunay asset can drive a cell outside the physical range, which will show up as a bright or dark speck that looks like a bad pixel. The intrinsic-Delaunay construction removes the failure and is a small amount of code. A test on a deliberately obtuse mesh would catch this.
  • Backward-Euler heat flow on a triangle mesh reduces to a pair of standard sparse symmetric-positive-definite systems that can be 'prefactored once and subsequently solved in near-linear time' — the basis of the heat method for geodesic distance, reported an order of magnitude faster than fast marching. source: Crane, Weischedel & Wardetzky, 'Geodesics in Heat', ACM TOG 32(5) 2013 — https://arxiv.org/pdf/1204.6216 and https://www.cs.cmu.edu/~kmcrane/Projects/HeatMethod/ for irsim: Implicit lateral conduction is cheap and unconditionally stable: prefactor (M + dt*alpha*L) once per asset at load and back-substitute each tick. This matters because irsim's tick is 1 s and the explicit stability limit for a 150 mm aluminium cell is well under that — an explicit lateral term would force a much smaller tick and break the fixed-tick contract in field.py.
  • The closest point method (Ruuth & Merriman, JCP 227(3), 2008) solves surface PDEs by replacing surface differentials with ordinary Cartesian differentials of the closest-point extension, on a narrow band of a 3D grid, supporting open surfaces and narrow-banding 'without loss of convergence order'. source: S. J. Ruuth & B. Merriman, 'A simple embedding method for solving partial differential equations on surfaces', J. Comput. Phys. 227(3), 2008; overview at https://arxiv.org/html/2305.04711v2 for irsim: The rigorous version of ADR 0087's rejected option 3, and worth recording as such: it is not 'voxels are wrong', it is 'a voxel grid without a closest-point extension is wrong'. But the narrow band must be thinner than the thinnest sheet in the scene, or both faces of a car panel again land in one band — so for vehicle/aircraft skins it needs a grid finer than the panel thickness, which is far more expensive than storing cells on the faces. Recommend recording as rejected-with-reason, not adopting.
  • NanoVDB is a GPU-friendly, linear-in-memory sparse volume format, portable across CUDA/OptiX/HLSL/GLSL, with variable-bit-rate quantisation typically reducing footprint 4-6x versus OpenVDB, optimised for random-access sampling from single GPU threads. (medium confidence) source: Museth, NanoVDB, SIGGRAPH 2021 Talks — https://dl.acm.org/doi/fullHtml/10.1145/3450623.3464653 for irsim: Relevant only if irsim later needs a genuinely volumetric field (plume, exhaust gas, fog cell structure) rather than a surface one. Warp exposes volume sampling, so the route exists. Not the answer for surface temperature.
  • Nanite stores vertex attributes quantised and bit-packed per 128 KB cluster page, and extra UV sets and custom vertex attributes increase per-cluster memory cost. (medium confidence) source: Karis, Stubbe & Wihlidal, 'A Deep Dive into Nanite Virtualized Geometry', SIGGRAPH 2021 Advances — https://advances.realtimerendering.com/s2021/Karis_Nanite_SIGGRAPH_Advances_2021_final.pdf for irsim: The mainstream engine answer to 'where does a per-point attribute live' is: on the vertices, compressed. For irsim the storage question is trivial at its scale — a float32 temperature on 50,000 vertices is 0.20 MB, on 500,000 vertices 2.0 MB, versus 1.05 MB for a 512² texture and 16.8 MB for 2048². Storage is never the constraint; adjacency correctness and cell-size-vs-gradient are.
  • Offline path tracers do transport these attributes: Blender Cycles ships UV, Position, Object Index and Material Index passes (explicitly documented as not anti-aliased) plus shader AOVs via an AOV Output node; Arnold writes built-in N, P, Pref AOVs and supports custom AOVs driven by shaders/user data. (1) It shows the missing capability is specific to Kit's RTX renderer, not to path tracing, which makes a feature request or an SPG probe well-founded and gives it a concrete target spec ('a non-anti-aliased UV pass and an integer primitive-id pass, as Cycles has'). (2) Cryptomatte's uint32-through-float32 trick is the proven pattern for moving an exact integer through a float channel — relevant if irsim ever needs a second exact id channel and only a float32 AOV is free. It is not a route through fp16.
  • Derived from standard property tables (aluminium k=237 W/m/K, rho=2700, c=900; steel k=50, rho=7850, c=490; asphalt k=0.75, rho=2300, c=920), the thermal diffusion length sqrt(alpha*t) over the physics-model §6.6 engine-bay rise time of 750 s is 270 mm for aluminium, 99 mm for steel and 16 mm for asphalt; over one hour, 593 mm, 216 mm and 36 mm. (medium confidence) source: Computed by me from textbook k/rho/c values (no single URL); method is the standard diffusion length sqrt(alpha t), alpha = k/(rho c) for irsim: A physics gap that the geometry work should close in the same breath. ADR 0087 uses 150 mm cells on a bonnet and the cells are thermally uncoupled, but aluminium smears heat 270 mm in the time the engine bay takes to warm — so irsim currently renders the bonnet hot spot sharper than reality, which is exactly the kind of structure a detector keys on. Asphalt, by contrast, genuinely needs no lateral term at these cell sizes, so the coupling can be a per-material switch (ADR 0083 says ablation switches are config). How production IR scene simulators (MuSES/RadThermIR, DIRSIG5, OKTAL S#

19 findings.

  • DIRSIG offers temperature at four distinct granularities and selects per material: per-material (THERM, Balfour, Data-Driven), per-solid-object (ODB/GLIST built-in temperatures), per-facet (temperatures embedded in GDB polygons; MuSES TDF import), and per-pixel (Map Temperature Solver, MappedBalfour). There is no single 'the' temperature granularity in a production scene — it is a per-material choice. source: DIRSIG Temperature Solvers manual, https://dirsig.cis.rit.edu/docs/new/temp_solvers.html for irsim: irsim should stop treating per-prim vs per-point as a binary. The production pattern is a tier selector per surface: a sky/sea background can stay per-material, a target skin per-facet, a bonnet or road per-cell. ADR 0087's 'a prim with no binding keeps its per-instance value' is already this pattern — name it explicitly and document the tiers so a scene author picks deliberately.
  • DIRSIG's built-in THERM solver is a 1-D slab with a user-defined thickness and documents two hard limits verbatim: "The THERM model does not support for internally driven heat fluxes that produce heat signatures like the warming on the hood of a car because of the hot engine beneath it" and "THERM is a 1D model and does not support conduction from 'connected' objects. For example, a hot surface on an airplane (because it is exposed to strong sun) does not laterally transfer heat to the portion of the plane in the shade." source: DIRSIG Temperature Solvers manual, https://dirsig.cis.rit.edu/docs/new/temp_solvers.html for irsim: The single most-cited academic IR scene simulator names irsim's exact two gaps as its own known limits — and names the bonnet-over-engine case as the canonical example. ADR 0088 already closes the internal-source half (and does it better than THERM, since it derives the falloff from a configuration factor). The lateral half is still open, and citing this doc in the ADR converts 'we skipped it' into 'we are at the DIRSIG tier and here is the next tier'.
  • DIRSIG's per-pixel path is a raster texture: "The input to this map is an ENVI image file with a single band. The value of the each pixel in that band is the temperature used", in degrees Celsius, applied by either a drape (XY) projection or a UV projection using facet-vertex texture coordinates, with GAIN/BIAS for 8-bit sources. source: DIRSIG Property Maps Manual, https://dirsig.cis.rit.edu/docs/new/maps.html for irsim: A 'temperature map' ingest is a small, well-precedented feature and it is irsim's escape hatch for anything the solver will not model (a prescribed aircraft skin, a measured thermal frame draped on a target, an externally solved hull). irsim's PlanarPatch is already a raster with a projection — a loader from a float32 array (or ENVI/NPY) into a patch is nearly free and matches DIRSIG's contract, including the °C-vs-K unit trap.
  • Temporally varying temperature maps are supported in DIRSIG5, with "addition of absolute time support and time interpolation to the .til (map time sequences) files", and spatially varying THERM inputs exist as "THERM parameter maps" (MappedTherm). The Balfour solver has a per-pixel variant; DIRSIG4's spatially constant per-material coefficients were replaced in DIRSIG5 "with the option to use spatially mapped coefficients". source: DIRSIG Release Notes, http://dirsig.cis.rit.edu/docs/new/ReleaseNotes.html ; DIRSIG demos TemperatureMap1 / MappedTherm1, https://dirsig.cis.rit.edu/demos/ for irsim: This validates irsim's core architectural bet: the state of the art for backgrounds is not a per-pixel PDE, it is an independent per-column solve whose parameters and forcing vary per pixel — which is precisely what ADR 0087 does ('no solver change was needed; the knobs existed'). It also suggests the cheapest next win: let a raster drive per-cell albedo/emissivity/thermal-inertia, so background texture is generated by physics rather than painted on.
  • When DIRSIG needs a genuine 3-D transient field it does not compute one — it imports MuSES. The MuSES TDF file carries the geometry and predicted temperatures; "The temperature results for each of the facets are loaded into DIRSIG and mapped back to the geometry" and "Thermal emissivities are pulled from the TDF file on a time and facet basis" (materials assumed diffuse). The plugin re-runs MuSES on a schedule: tdf_time_duration default 1800 s, tdf_time_resolution default 900 s, so "the plugin will start by having MuSES compute 3 times for 0, 900 and 1800 seconds". source: DIRSIG MuSES Plugin manual, https://dirsig.cis.rit.edu/docs/new/muses_plugin.html for irsim: Two lessons. (1) The renderer/solver boundary in production is a per-facet temperature array at a sparse set of timesteps, not a live coupling — irsim's point_bridge is the same shape and can stay so. (2) The thermal cadence is coarse (900 s) relative to the frame rate; irsim's 1 Hz DEFAULT_TICK_S and between-tick interpolation is already more than production does, which is worth recording as headroom rather than spending more on it.
  • MuSES discretises a 3-D surface mesh and builds the conduction network automatically in both directions: "This mesh is used for automatic view factor calculation, lateral and vertical conduction via automatic nodal network generation, radiative and convective … heat transfer. The depth of each portion of the surface mesh is handled virtually by a user-supplied thickness that allows analysts to study the impact of surface thickness without needing to regenerate the 3D mesh. Element-to-element and/or part-to-part thermal links can also be defined … Physical temperatures are calculated for all elements at each discrete timestep." source: DeMars et al., "High-Fidelity Simulation of Dynamic Thermal Satellite Signatures with MuSES", AMOS 2023, https://amostech.com/TechnicalPapers/2023/Poster/Demars.pdf for irsim: The gold-standard target code carries lateral conduction and treats thickness as a per-element scalar attached to a surface mesh rather than as real volume geometry. That is exactly the abstraction irsim already has (a facet with a thickness) — so the upgrade path is additive: give PlanarPatch cells a neighbour graph (trivial on a regular grid) and an N-layer stack, without ever meshing a volume.
  • MuSES places several thermal nodes through the thickness of one element: its user-routine API provides functions "to determine the position of the thermal node within (the thickness of) each element, the element number, the part to which the element belongs, and the spatial position of the element … different properties can be calculated for and applied to each thermal node", and temperature-dependent properties are evaluated "once per iteration per thermal node". source: Curran & Gonda (ThermoAnalytics / US Army TARDEC), "Applications of the MuSES Infrared Signature Code", NATO RTO-MP-SCI-145 paper 14, https://publications.sto.nato.int/publications/STO%20Meeting%20Proceedings/RTO-MP-SCI-145/MP-SCI-145-14.pdf for irsim: irsim's two_node.py is a 2-node version of this and is the right seed. Generalising it to an N-layer stack per cell (not per facet) is what lets a 1 mm steel bonnet and 0.3 m of asphalt share one solver with honest time constants — the bonnet needs layers to respond in minutes, the asphalt needs them to carry yesterday.
  • MuSES is the same code as RadTherm/IR: "MuSES (known as RadTherm/IR outside of the USA)". Its transient restart chains simulations — view factors and conductors are recomputed at each restart, and a restart "requires … the same number and assignment of thermal nodes"; it is used for a continuously running prediction system fed 12-hourly weather forecasts. source: Curran & Gonda, NATO RTO-MP-SCI-145-14, https://publications.sto.nato.int/publications/STO%20Meeting%20Proceedings/RTO-MP-SCI-145/MP-SCI-145-14.pdf for irsim: Collapses two of the six named products into one solver — the RadThermIR validation literature is MuSES literature. Also: the restart-invariance rule ('same number and assignment of nodes') is a good constraint for irsim's spin-up cache key, which currently hashes facet properties; a patch that changes n_u/n_v must invalidate it, and a test should pin that.
  • Fraunhofer IOSB's large-scene model gives each triangle a prism ("surface volume") with N inner layers — "for each triangle overall 2+N temperature values have to be stored: the surface temperature, N temperature values for every layer, and the core temperature" — with lateral conduction discretised by finite volume across triangle edges (flux summed as (1/A_i)·Σ L_ij (∇T)_ij·n_ij) and forward Euler time integration where "a time step of Δt = 30s leads to stable results", chosen "after a stiffness analysis of the linear system". source: Kottler, Burkard, Bulatov & Haraké (Fraunhofer IOSB), "Physically-based Thermal Simulation of Large Scenes for Infrared Imaging", GRAPP 2019, https://www.scitepress.org/Papers/2019/73514/73514.pdf for irsim: This is the closest published analogue to what irsim should build next, and it is a free, citable, reproducible design: prism per cell, 2+N stored temperatures, FVM lateral flux, explicit Euler at 30 s. Sim-to-real transfer for thermal object detection#

26 findings.

  • On LWIR ground-to-air drone detection, a detector trained only on synthetic IR recovers 63-72% of the mAP@50:95 of the same architecture trained on only 100 real LWIR images. Measured across 8 architectures: YOLOv13 n/s/l/x synthetic-only 0.409/0.378/0.382/0.386 vs real-only 0.567/0.577/0.593/0.616; RF-DETR n/s/m/l synthetic-only 0.437/0.474/0.467/0.463 vs real-only 0.620/0.670/0.663/0.698. At mAP@50 the gap is much smaller (synthetic-only 0.670-0.893 vs real-only 0.847-0.976), i.e. synthetic data teaches 'where', not 'how well'. source: Liiv, Soodla, Bignoumba, Liezenga, Pruuden, 'Training with synthetic data for drone detection in thermal imagery', arXiv:2608.17799 (18 Aug 2026), Table 8 / Appendix G for irsim: This is the number ME.7's synthetic_to_real protocol should be benchmarked against. If irsim's physically-grounded renders do not beat ~0.47 mAP@50:95 synthetic-only on a comparable LWIR drone validation set, the physics is not buying anything over a FLUX+Blender IR-like pipeline. Set that as the explicit exit criterion rather than an absolute AP.
  • Synthetic pre-training followed by fine-tuning on only 100 real LWIR images beat real-only training in every one of nine configurations, by +0.015 to +0.063 mAP@50:95 (and by +0.352 for Faster R-CNN, whose real-only baseline collapsed to 0.012). Best overall: RF-DETR-L at 0.723 with dual-modality fine-tuning. Authors' conclusion: 'synthetic pre-training provides a useful addition to (few-shot) real-data fine-tuning but does not replace in-domain LWIR data.' source: Liiv et al., arXiv:2608.17799, Table 8 and Section 6 for irsim: ME.7's mixed_to_real protocol is the one that will produce a positive result and it needs almost no real labels — 100 images. That reframes the ME.7 blocker: the project does not need the full Halmstad label export, it needs ~100-200 Python-readable boxes from any public LWIR set.
  • The single largest measured statistical divergence between real LWIR imagery and a synthetic pipeline is the AGC/16-to-8-bit quantisation signature: full-image Histogram Total Variation, Cohen's d = 1.242 (real median 0.306 vs synthetic 0.101). Real thermal frames show a comb-like quantisation pattern from scene-adaptive AGC stretching 14/16-bit raw into 8 bits; synthetic pipelines produce a continuous histogram. Dynamic-range utilisation is fourth-largest (d = 0.899; real median 196 codes vs synthetic 164). source: Liiv et al., arXiv:2608.17799, Appendix D (Table 4, Table 5) for irsim: irsim's ISP already has agc_plateau/agc_linear, but the rendered output histogram must carry the sparse-code comb a real 16→8 remap leaves behind, and the Tier-4 report must measure it. This single statistic outranks every radiometric quantity the project has been tuning, and irsim is one of very few simulators that can produce it honestly because it starts from real 16-bit radiance.
  • The second-largest divergence is per-point target heat structure: target-crop Sobel Gradient Variance is over four times higher in real LWIR detections than in synthetic ones (Cohen's d = 1.224), and target-crop GLCM entropy differs at d = 0.974. The authors' wording: real drones display structural complexity from 'uneven heat distribution, sensor noise, and optics — factors largely absent in the comparatively uniform meshes of the synthetic pipeline', confirming 'the simulated drones act as uniform silhouettes rather than noisy, physical heat sources.' source: Liiv et al., arXiv:2608.17799, Section 4.3 and Appendix D for irsim: This is the owner's headline requirement — per-point temperature, not one value per object — showing up as the #2 ranked, quantified sim-to-real gap driver in the current SOTA paper. ADR 0087 (PlanarThermalField) and ADR 0088 (spatial heat sources) are a direct fix for a published, measured defect. Target-crop Sobel gradient variance is the statistic that would demonstrate it; irsim should measure it on its own renders against real crops.
  • Macro-level spatial noise texture is NOT the hard part: applying plain additive Gaussian + Poisson noise and a 5x5 Gaussian blur as post-processing brought the synthetic set's full-image GLCM statistics essentially onto the real ones (GLCM correlation 0.994 synthetic vs 0.977 real; GLCM entropy 9.862 vs 9.786), while the AGC and target-structure gaps remained wide open. source: Liiv et al., arXiv:2608.17799, Appendix D (Table 4) for irsim: A caution against over-investing in noise realism for sim-to-real specifically. irsim's noise chain (3-D noise, FPN, bad pixels, NUC residual) is physically justified for NETD/Tier-2 work, but the evidence says it will not be what moves a detector. Spend the next sim-to-real steps on the ISP and the temperature field, and treat the noise chain as already sufficient for Tier 5 until an ablation says otherwise.
  • Changing only the 16→8-bit tone mapping — identical frames, identical detector, identical weights protocol — moves detection mAP on FLIR-ADAS by 14 to 33 points. RetinaNet: RAW 20.1, Min-max 22.3, HE 23.4, Clip 24.1, FLIR AGC 25.2, TCNet 34.7. YOLO-X: RAW 37.9, HE 40.7, Clip 49.1, Min-max 50.8, FLIR AGC 53.5, FieldScale 54.0, TCNet 56.0. Sparse-RCNN: RAW 12.3 → TCNet 45.7. On STheReO, Sparse-RCNN goes RAW 4.1 → TCNet 39.5 (nearly 10x). source: Lee et al., 'Thermal Chameleon: Task-Adaptive Tone-mapping for Radiometric Thermal-Infrared images', arXiv:2410.18340, Tables II and III for irsim: The ISP is a larger lever on detector performance than anything in the radiometric chain. Two consequences: (1) any Tier-5 comparison that does not fix and report the tone mapping is measuring the tone mapping, not the simulator — this belongs in ADR 0085's protocol; (2) irsim can emit RAW-16 and AGC-8 from the same frame, which no indexed public set provides, so a paired RAW/display release is a genuinely novel contribution rather than a me-too dataset.
  • The tone-mapping effect is worst exactly in the small-target regime irsim targets. FLIR-ADAS RetinaNet mAP@small: RAW 6.1, FLIR AGC 14.7, FieldScale 14.5, TCNet 22.7 — a 3.7x swing on small objects from the ISP alone, versus a 1.4x swing on mAP@large (58.4 → 67.7). source: Lee et al., arXiv:2410.18340, Table II for irsim: For sky-background targets at 2 km subtending a couple of pixels, the display mapping dominates. This validates irsim's existing decision (ME.7 docstring) to make P_d-vs-SCR and small/tiny-restricted AP the headline metrics instead of a single pooled AP.
  • On maritime TIR small-target segmentation with synthetic data from the ARMA 3 game engine: translated-synthetic-only reaches mIoU 82.2 / recall 88.2 / precision 73.2 / F1 80.0 against real-only mIoU 92.7 / recall 92.1 / precision 92.2 / F1 92.1. So mIoU recovers 89% of real but precision collapses to 79% — the synthetic-trained model false-alarms. Synthetic + real together gives 93.1 mIoU, marginally above real-only (+0.4). source: Kim et al., 'Thermal-Infrared Remote Target Detection System for Maritime Rescue based on Data Augmentation with 3D Synthetic Data', arXiv:2310.20412, Table II for irsim: For the maritime lane (MS.*), the metric that exposes the gap is precision / false-alarms-per-frame, not IoU or recall. irsim's false_alarms_per_frame already exists in irsim_eval.detection; make it a required cell in the maritime Tier-5 report rather than an optional one.
  • Domain-adapting synthetic TIR toward the real sensor domain — explicitly to 'generate real-like noise and clutter, eliminating artificial texture' — improved the synthetic-trained model from mIoU 82.6 / F1 78.1 (raw game source) to mIoU 86.7 / F1 84.4 (translated source): +4.1 mIoU, +6.3 F1 on the same real test set, from sensor-domain realism alone. source: Kim et al., arXiv:2310.20412, Table III for irsim: A quantified value for exactly what irsim's detector/noise/ISP chain does natively, and which a GAN has to learn. It is the strongest published argument that a physics-first simulator should beat an image-translation pipeline — and it gives the size of the prize: about 4-6 points.
  • On KAIST thermal pedestrians with GAN-synthesised thermal images: synthetic-only log-average miss rate is 45.88% (all) / 54.37% (day) / 26.04% (night) against real-only 28.46 / 36.32 / 11.97. The best mixture is 90% real + 10% synthetic at 25.62% (2.84 points better than real-only); 80/20 gives the best night result at 11.12%. Miss rate improves monotonically with the real fraction up to ~90%. source: Marnissi et al., 'Robust pedestrian detection in thermal imagery using synthesized images', arXiv:2102.02005, Table I for irsim: An explicit synthetic/real mixing curve. ME.7's mixed_to_real protocol should sweep the ratio rather than test one mix — the optimum here is only 10-20% synthetic, which is a very different operating point from 'replace the real data'.
  • A detector trained exclusively on diffusion-generated synthetic thermal data reaches 0.372 mAP on FLIR-Aligned, with near parity on the person class against a fully fine-tuned Grounding-DINO. The same paper measures the domain shift with FID: synthetic-vs-FLIR-Aligned is 41.40, compared with 38.74 between two real thermal benchmarks (FLIR-V2 vs FLIR-Aligned) — i.e. the synthetic-to-real distance is comparable to the distance between two real datasets. source: Ranasinghe, Schenck, Yellin, Hu, Funk, Patel, 'Thermal-Det: Language-Guided Cross-Modal Distillation for Open-Vocabulary Thermal Object Detection', arXiv:2605.10130, Supplementary S7 for irsim: The methodological move irsim's ADR 0085 gap score is missing: a bare AUC or FID is uninterpretable, but the same statistic measured between two real sets is the yardstick. irsim's datasets.yaml already indexes six public sets — pick two real ones, compute the real-vs-real gap score, and report every synthetic-vs-real number beside it. This is a small change that makes every Tier-4 number mean something.
  • Feature-space domain gap measured as Kernel DINO Distance (KID computed over DINOv2 features, x1000, bootstrapped over 500 subsets of 50): real-but-different-sensor set 262.29 ± 39.85 (full image) and 84.33 ± 13.68 (target crop); synthetic set 332.39 ± 41.95 and 159.53 ± 20.18. So the synthetic gap is ~1.27x the real-to-real gap at full-image level but ~1.89x at target-crop level. source: Liiv et al., arXiv:2608.17799, Appendix E (Table 6) for irsim: Full-frame and crop-level gaps tell different stories, and the crop level is where the per-point temperature requirement lives. irsim's discriminator currently scores patches; it should score target crops separately from background patches and report both, because a simulator can match the background and still render targets as uniform blobs.
  • Intensity-histogram Earth Mover's Distance against the same real validation set: synthetic 29.88, synthetic+RGB-birds 52.80, a real but differently-sensored LWIR set 18.77, and a better-matched real set 13.61. Substantial distributional shift exists even among real datasets, because 'physical IR cameras apply proprietary, dynamic AGC stretching logic that fundamentally alters the radiometric profile of the scene based on specific hardware'. source: Liiv et al., arXiv:2608.17799, Appendix D for irsim: Directly comparable to irsim's own histogram EMD in DN8 (irsim.validation.compare, ADR 0085). It gives a concrete pass band: an EMD near 13-19 codes is what two real sets differ by, so a synthetic set landing under ~20 is at parity with real-sensor variation, and ADR 0068's untargeted EMD check can be given a measured threshold instead of a guessed one.
  • Over-diverse synthetic backgrounds are a liability, not an asset. The synthetic set's full-image Vendi Score (effective number of visual concepts) was 134.6 against 39.6 for the real validation set and 32.3 for a real source set — 3.4x inflated — because real thermal backgrounds 'naturally wash out into low-contrast, low-variance states as scenes approach thermal equilibrium', while the synthetic pipeline kept dense high-frequency geometric detail. That inflated diversity drove the domain gap and did not improve performance; at the target-crop level synthetic diversity (22.5) matched real (23.7) yet crop KDD stayed 1.9x worse, so 'matching morphological diversity alone is insufficient to close the thermal domain gap.' source: Liiv et al., arXiv:2608.17799, Section 4.4 and Appendix E/F for irsim: An argument against spending steps on background photorealism or scene-library breadth, and for physically correct background temperature fields that actually approach equilibrium. It also supports the demo-scenes-must-look-real memory being about legibility for the human, not about training-set diversity — those are different goals and should not be conflated in a roadmap step.
  • Geometry and viewpoint alignment can outweigh every appearance factor. In a Blender-Cycles thermal aerial pipeline, ablating only the camera pitch distribution moved drone mAP@0.5 from 0.464 (fixed 0 degrees) to 0.981 (random 0-90 degrees) to 0.995 (pitch drawn from the real dataset's own metadata) — the largest single ablation in the paper. Final results: HIT-UAV-drone overall mAP@0.5 0.898 / mAP@0.5:0.95 0.673; MONET-deer 0.821 / 0.569. Thermal vs visible for the same drone task: 0.995 (HIT-UAV thermal) vs 0.429 (DUT-Anti-UAV visible). source: Barisic Kulas, Jurasovic, Bogdan, 'Unlocking Thermal Aerial Imaging: Synthetic Enhancement of UAV Datasets', arXiv:2507.06797 / ECMR 2025, DOI 10.1109/ECMR65884.2025.11163192 for irsim: Before any further physics fidelity work for the sim-to-real lane, check that irsim's scene configs sample camera elevation, slant range and target aspect from distributions matched to the intended validation set. This is a cheap config change with a measured effect larger than anything in the radiometric chain.
  • Real thermal sensor noise is heteroscedastic and spatially structured, and uniform synthetic noise augmentation cannot stand in for it: 'The real domain noise exhibits greater variability, whereas the synthetic noise is uniform and cannot capture the dynamic heteroscedastic nature of noise'. Separately, denoisers trained on synthetic Gaussian noise are reported to be incapable of handling real fixed-pattern/strip noise. (medium confidence) source: Ivan-ISTD, 'Rethinking Cross-domain Heteroscedastic Noise Perturbations in Infrared Small Target Detection', arXiv:2510.12241, Fig. 2; and TIR-Diffusion, arXiv:2508.03727 for irsim: Qualifies the earlier finding: naive additive noise closed the macro texture gap but the literature says it does not close the structured noise gap (FPN, striping, signal-dependent variance). irsim's 3-D noise + FPN + NUC-residual chain is the right model; the open question is whether the structured part shows up in a detector metric. That is a clean ablation for ADR 0083's existing config switches.

  • Standard evaluation protocol in this literature: (a) detection metrics AP@0.5 and AP@0.5:0.95, plus AP restricted to small/tiny, plus P_d vs SCR where SCR = (target mean - local background mean) / local background sigma; KAIST convention uses log-average miss rate vs FPPI instead; infrared small-target work uses mIoU/nIoU/P_d/F_a. Validating an IR simulator without the camera#

31 findings.

  • The NVESD 3D noise model decomposes an imager noise cube into seven orthogonal components (N_TVH random spatio-temporal, N_TV temporal row/streaking, N_TH temporal column/rain, N_VH random spatial, N_V fixed row, N_H fixed column, N_T frame-to-frame) plus the cube mean S, derived with directional averaging operators D_t, D_v, D_h applied as products of (1-D) and D factors. Total temporal noise = sqrt(N_TVH^2 + N_TV^2 + N_TH^2 + N_T^2); total spatial noise = sqrt(N_VH^2 + N_V^2 + N_H^2). The inverse conversion is not possible. source: K. Chrzanowski, 'Critical review of present-day methodology of thermal imager noise characterization', Metrol. Meas. Syst. 32(2), 2025, Table 3 and eqs. (10)-(13) — https://metrology.wat.edu.pl/earlyaccess/32/2/MMS-01673-2024-02-Early-Access.pdf (citing D'Agostino & Webb, Proc. SPIE 1488, 110-121, 1991) for irsim: src/irsim/validation/noise.py already implements this with the leakage-corrected (unbiased) mean-square solution, which is the right choice. Two gaps: (a) it does not report the two summary quantities N_temp and N_spat that every external comparison is quoted in, and (b) the docstring should cite Chrzanowski's eq. numbers so a reader can check the operator algebra against a published source rather than against the code.
  • NV-IPM's Measured System Component — the standard hand-off from a lab measurement into a range-performance model — carries only four of the seven 3D-noise components: Sigma TVH, Sigma VH, Sigma V, Sigma H, all in Kelvin. Alongside them it carries Horizontal/Vertical Pre-Sample MTF as arrays in cycles/pixel, a Normalized Response array (the SITF), detector counts, FOV, detector pitch, display contrast and frame rate. source: A. Irwin, 'Performance prediction from EO system measurements using IRWindows and NV-IPM', Proc. SPIE 10625, 1062502 (2018), Table 1 — https://www.sbir.com/PDFs/SPIE-Std-Products-Publications/PerformancePredictionfromEOSystemMeasurements.pdf for irsim: This is the canonical export format for 'what a measured IR camera is'. irsim can emit exactly this object from its own simulated benches (SITF + 3D noise + slant-edge MTF), which turns the Tier 2 bench suite into something a third party can independently range-check in NV-IPM — a validation route that needs no camera at all, only the free NV-IPM model.
  • The standard laboratory sequence for characterising an imager for NV-IPM is three tests with these conditions: SITF as a differential sweep from -10 to +20 C in 5 C steps against an extended blackbody with a linear best fit over -5..+15 C; 3D noise from 128 frames at an absolute 25 C flood/flat-field; MTF by ISO 12233:2014 slanted edge, 128 frames averaged, at a 20 C differential, reported at 0.5 cycles/pixel. source: A. Irwin, Proc. SPIE 10625, 1062502 (2018), Figure 6 test configurations — https://www.sbir.com/PDFs/SPIE-Std-Products-Publications/PerformancePredictionfromEOSystemMeasurements.pdf for irsim: src/irsim/validation/bench.py's SITF should adopt these conditions verbatim (differential sweep, linear fit window, 128-frame cubes) so that its numbers are directly comparable to any published measured-system component. Right now the bench's temperature list and frame count are project-chosen, which makes cross-comparison an argument rather than a lookup.
  • NETD is defined as N_im / SiTF, but there is no agreed definition of N_im: the review tabulates at least five distinct definitions in current use (total spatio-temporal noise, average-power temporal noise, average-intensity temporal noise, median-power temporal noise, random spatio-temporal noise), drawn from FPA vendors, camera vendors, ASTM, test-equipment vendors and NVESD itself. NVESD's own published recommendation changed across 1992, 2005 and 2023 papers. source: K. Chrzanowski, Metrol. Meas. Syst. 32(2), 2025, Tables 1 and 2 — https://metrology.wat.edu.pl/earlyaccess/32/2/MMS-01673-2024-02-Early-Access.pdf for irsim: Every place irsim writes 'NETD' (configs/sensors/*.yaml netd_mk_at_300k, validation/bench.py measured_netd_k, docs/physics-model.md section 9.4) must say which of the five it means. The project's own convention appears to be average-intensity temporal noise of the TVH component; stating that explicitly in an ADR costs one paragraph and prevents a silent factor-of-two disagreement with any external number.
  • The choice of low-frequency de-trending filter changes the measured temporal noise of an uncooled imager by up to a factor of three, and the effect varies between imagers. Normalised to the unfiltered result: uncooled imager 1 gives 1.00 / 0.68 (2nd-degree polynomial) / 0.55 (Gaussian sigma=8 frames); imager 2 gives 1.00 / 0.85 / 0.34; imager 3 gives 1.00 / 0.99 / 0.97; a cooled imager gives 1.00 / 1.00 / 1.00. No standard prescribes the filter, and NVESD papers have used no filtration (1992), a 2nd-degree polynomial (2005), and a Gaussian (2023). source: K. Chrzanowski, Metrol. Meas. Syst. 32(2), 2025, Section 6.2 and Table 5 — https://metrology.wat.edu.pl/earlyaccess/32/2/MMS-01673-2024-02-Early-Access.pdf for irsim: This is the single most consequential caution for the whole ME lane. It means a temporal-noise number measured off a public clip is only reproducible if the de-trending is stated, and it is a bigger effect than the codec floor ADR 0068 already guards against. decompose_3d and temporal_shape should take an explicit detrend argument and every reported sigma should carry the convention; a report that does not is not falsifiable.
  • The FLIR Boson datasheet does not quote a scalar NETD — it quotes three 3D-noise components. Table 13 'Temporal NEDT in high-gain state': Industrial <40 mK random temporal (tvh), <14 mK column noise (th), <14 mK row noise (tv); Professional 50/18/18 mK; Consumer 60/21/21 mK.   • VDI/VDE 5585-1 prescribes two NETD methods. Method A: record at least 100 consecutive frames of a uniform blackbody at the working integration time and frame rate, compute each pixel's temporal standard deviation, and take NETD as the mean of those. Method B: use two sequential images and a difference formula with a sqrt(2) correction. Measured uncooled microbolometer values at a 100 C reference are roughly 50-80 mK depending on camera and method. The same standard family defines IETD (inhomogeneity equivalent temperature difference) for spatial noise and the size-of-source effect, which is ~0.8-1.0 K for uncooled microbolometers against ~0.1-0.2 K for cooled MCT; expanded calibration uncertainty (k=2) for an uncooled camera at 100 C is typically 1.5-2.0 K. source: Metrological characterization and calibration of thermographic cameras for quantitative temperature measurement, J. Sens. Sens. Syst. 9, 425 (2020), open access — https://jsss.copernicus.org/articles/9/425/2020/ for irsim: Two things follow. (a) The 100-frame minimum and the per-pixel-then-average order (not variance-then-sqrt) is a concrete convention for bench.py's measured_netd_k. (b) Size-of-source effect is a real uncooled-camera phenomenon irsim does not model — stray light from outside the nominal target subtense reaching the detector. At 0.8-1.0 K it is larger than most of the effects the project does model, and deserves at minimum a named entry in docs/spec-issues.md as a known omission.

(medium confidence) source: Determining atmospheric aerosol content with an infra-red radiometer, arXiv:1212.4426 — https://arxiv.org/html/1212.4426 ; W. L. Smith and R. Toumi, 'Measuring Cloud Cover and Brightness Temperature with a Ground-Based Thermal Infrared Camera', J. Appl. Meteor. Climatol. 47(2), 2008 — https://journals.ametsoc.org/view/journals/apme/47/2/2007jamc1615.1.xml for irsim: Directly relevant to ADR 0044, ADR 0071 and src/irsim/validation/aerial.py's zero_contrast_elevation, which depends entirely on how cold the sky gets and how fast it warms toward the horizon. The zenith figure of roughly -70 C for a clear, dry sky is a sanity bound the sky model should reproduce, and the aerosol sensitivity (about 14 C swing) says the aerosol scaling in ADR 0049 is not a second-order detail for sky-background contrast. Marked medium because the zenith-angle parameterisation itself is behind a paywall and was not read in full.
  • Sea-surface infrared emissivity models are validated by in-situ angular radiometry: measurements with a CE 312 four-channel radiometer in the 8-14 um interval, with sea temperature from high-precision probes on oceanographic buoys, at several view angles and wind speeds. The Masuda model is validated for observation angles up to about 50 degrees; beyond that, multiple reflections at the roughened surface produce discrepancies and the Wu and Smith model is required for the 8-13 um range. Emissivity falls roughly 2-3% by a 55 degree view angle. (medium confidence) source: In situ angular measurements of thermal infrared sea surface emissivity - Validation of models, Remote Sens. Environ. (2004) — https://www.sciencedirect.com/science/article/abs/pii/S003442570400286X ; Measurements of the infrared emissivity of a wind-roughened sea surface, Appl. Opt. 44(3), 398 (2005) — https://opg.optica.org/ao/abstract.cfm?uri=ao-44-3-398 for irsim: Gives the maritime lane (ADR 0078 analytic sea, ADR 0080 sea skin temperature) a published validity envelope rather than an assumption: a single-scattering Fresnel-plus-slope-distribution model is defensible to about 50 degrees from nadir and understates emissivity beyond that. For a shore-based or low-altitude maritime camera most of the sea surface is viewed at grazing angles well past 50 degrees, so this is the regime the simulator will actually be in, and the multiple-reflection term is not optional there. Worth recording in docs/spec-issues.md with the angle at which the analytic model is known to break.
  • MTF measured from real imagery is bounded by what the imagery is. The slanted-edge method requires a straight, high-contrast edge tilted slightly to the array axes so that binning by distance from the edge produces an oversampled ESF; blind MTF estimation from natural images without a test chart exists but is research-grade and relies on texture-rich sub-images and iterative kernel estimation. Traditional methods require standardised test charts, yield few measurements across the field, and need careful calibration. (medium confidence) source: ISO 12233 slanted-edge method as applied to IR arrays: 'Measurement of the Modulation Transfer Function of Infrared Imaging System by Modified Slant Edge Method', J. Opt. Soc. Korea (2016) — https://koreascience.or.kr/article/JAKO201620240542566.page ; 'Automatic Estimation of Modulation Transfer Functions', arXiv:1805.01872 — https://arxiv.org/pdf/1805.01872 ; on-orbit blind MTF via refined image kernels — https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10181510/ for irsim: Confirms that ADR 0068's exclusion of edge_spread on the Halmstad set is the right call for the right reason, and sets the honest ceiling on what src/irsim/validation/mtf.py can claim from public data: an ESF width in pixels is comparable (it is a length, and no display mapping changes it), but an absolute MTF curve from a lossy 8-bit clip is the system MTF convolved with the codec's own transfer function and should never be compared against a lens specification.
