ir-radiometry

Radiometric physics for the IR camera simulator — Planck's law, band integration, radiance LUTs, apparent temperature inversion, thermal derivatives, and radiometric unit conventions. Use this skill whenever the task touches blackbody radiance, spectral bands, wavelength or wavenumber, W/m2/sr, photon flux, LUT generation, emissivity-weighted radiance, temperature-to-radiance conversion, or NETD scaling — even if the request just says "compute the signal" or "convert temperature to pixel value". Also use it before adding any new spectral band, since band definitions live in this layer.

Unit convention — one convention, enforced#

Ambiguity about π and about per-µm vs per-m is the single largest source of silent radiometric error.

  • Wavelength is always µm. Never metres, never nanometres, never wavenumber.
  • Spectral radiance is always W·m⁻²·sr⁻¹·µm⁻¹. Variable names start with L_.
  • Band radiance is W·m⁻²·sr⁻¹. Variable names start with Lb_.
  • Exitance is W·m⁻², names start with M_. Relationship for a Lambertian surface: L = M / π.
  • Photon quantities mirror this with a _q suffix: L_q, Lb_q, units ph·s⁻¹·m⁻²·sr⁻¹[·µm⁻¹].
  • Temperature is always Kelvin, float32 minimum, name T_*. Celsius only at the UI boundary.

Any function that returns radiance states its units in the docstring's first line. Any function that takes a wavelength array asserts it is monotonic increasing and in a plausible µm range (0.1–100).

The two Planck forms#

L(λ,T)   = C1L / (λ**5 * (exp(C2/(λ*T)) - 1))     # W·m⁻²·sr⁻¹·µm⁻¹
L_q(λ,T) = C1Q / (λ**4 * (exp(C2/(λ*T)) - 1))     # ph·s⁻¹·m⁻²·sr⁻¹·µm⁻¹

Use the photon form for photon detectors (MWIR/SWIR/NIR — quantum efficiency is per-photon) and the energy form for bolometers (uncooled LWIR — the membrane absorbs power). Getting this backwards produces an error that varies across the band, so it does not show up as a simple gain offset.

Numerical care: for large x = C2/(λT) (cold scenes, short wavelengths) exp(x) overflows. Use np.expm1(x) for the denominator and clip x at ~700 before exponentiating. Add a test at T = 200 K, λ = 0.8 µm — it will overflow a naive implementation.

Band integration#

Lb(T) = ∫ R(λ) L(λ,T) dλ where R(λ) is the normalised spectral response.

Two paths, both needed:

Reference path — direct quadrature (Simpson) on a 0.01 µm grid with the real R(λ). Slow, correct, used as the oracle in tests and for LUT generation.

Fast path — precomputed LUT, 200–1000 K at 0.05 K spacing, float32, linear interpolation. One table per band per quantity (Lb, Lb_q, dLb_dT). ~16k entries, 64 kB. Generated by make luts and checked into data/lut/ with a hash of the config that produced it, so a stale LUT is detectable.

A third form is useful for validation and for top-hat responses — the closed-form fractional exitance:

F(λT) = (15/π⁴) Σ_{n≥1} (exp(-n·x)/n) · (x³ + 3x²/n + 6x/n² + 6/n³),   x = C2/(λT)
Lb(T) = (σT⁴/π) · [F(λ₂T) − F(λ₁T)]

Converges in 3–8 terms for x > 2. Use it to cross-check the quadrature path — if the two disagree by more than 0.1% on a top-hat response, one of them has a bug.

Apparent temperature#

Lb(T) is monotonic, so invert by binary search on the LUT (or a precomputed inverse table).

Keep the distinction sharp in naming and in your head:

  • T_kinetic — the true physical surface temperature. Ground truth. The scene knows it.
  • T_apparent — what the camera reports. Lb⁻¹(L_measured).

They differ by exactly the emissivity + reflection + atmosphere error. That difference is the product. A pipeline that returns T_kinetic as the camera output has simulated a temperature probe, not a camera. If you find yourself tempted to shortcut through the true temperature, that is a bug in the design, not a convenience.

Thermal derivative#

dL_dT(λ,T) = L(λ,T) · (C2/(λ·T²)) · exp(x)/(exp(x)−1),   x = C2/(λT)

Tabulate in-band alongside Lb. This is what NETD divides by, and it is why NETD falls as scene temperature rises. Any code that treats NETD as a scene-independent constant in Kelvin is wrong — see the sensor-noise-chain skill.

Invariants to assert in tests#

These catch real bugs, not typos:

  1. L_q(λ,T) · h·c/λ == L(λ,T) to 1e-12 relative. Catches a wrong C1Q.
  2. ∫₀^∞ L(λ,T) dλ == σT⁴/π to 1e-6. Catches a wrong C1L or a π error.
  3. Lb_lut(T) vs Lb_quadrature(T): max error < 5 mK equivalent over 200–1000 K. Express the tolerance in mK, not in radiance — radiance tolerances are meaningless to read.
  4. Lb⁻¹(Lb(T)) == T to < 1 mK over the full range.
  5. dLb_dT vs central finite difference of Lb: < 1e-5 relative.
  6. Lb(T) strictly increasing in T.
  7. Wien: argmax_λ L(λ,T) · T == 2897.77 to 0.1%.
  8. No overflow, no NaN, no negative radiance anywhere on a 200–2000 K × 0.4–20 µm sweep.

Adding a band#

A band is a data file, not code. Adding one should touch:

  • configs/sensors/<name>.yaml — range, spectral response path, regime (emissive/reflective/mixed)
  • data/spectra/<detector>.csv — λ, R(λ), normalised
  • make luts to generate the tables

and nothing in irsim/radiometry/. If adding a band requires editing radiometry code, stop and fix the abstraction — scalability across bands is a core requirement of this project.

Common failure modes#

  • Mixing per-µm and per-m spectral radiance. Factor of 1e6, so it is obvious once you look — but people don't look, because the AGC rescales it away and the image still looks correct.
  • Dropping or double-applying π when converting exitance to radiance. Factor of ~3.14, easily mistaken for an emissivity error.
  • Normalising R(λ) when you shouldn't, or failing to when you should. Decide once: R(λ) is normalised to peak 1.0, and absolute responsivity lives in the detector model. Document it in the loader and assert it.
  • Generating a LUT from one config and using it with another. Hence the config hash.
